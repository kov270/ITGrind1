# Алгоритмы банковских счетов

## Фиксированные значения

Все закрытые наборы вариантов объявлены в enums.py. Конструкторы и чекеры
принимают правильный Enum или совместимую строку. check_enum() возвращает
элемент нужного класса и отклоняет неизвестные значения и чужие перечисления.
Внутренние сравнения и присваивания используют Enum, а не строковые литералы.
Валюты, типы активов и пары валют в настройках также нормализуются к Enum.
Поля account.status, client.status, transaction.status имеют разные перечисления.
Тип транзакции не смешивается с типом счёта.
Уровни и причины риска, важность, события аудита и действия безопасности
имеют свои перечисления. Сообщения об ошибках остаются свободным текстом.
Информационные словари и JSONL сохраняют .value; AuditLog нормализует
содержимое записи к JSON-совместимому виду, чтобы чтение файла давало тот же результат.

## Создание клиента

1. Проверить ФИО как непустую строку (без требования ровно трёх слов).
2. Проверить возраст: целое число, не меньше 18. bool и дробные числа запрещены.
3. Проверить контакты: непустой словарь непустых строк; создать его копию.
4. Проверить статус клиента: active или blocked.
5. Сгенерировать client_id через UUID и сохранить данные.
6. Создать отдельный пустой список account_numbers для нового клиента.

## Управляющий класс Bank

add_client регистрирует нового Client с пустым списком счетов.
Пароль хранится как PBKDF2-HMAC-SHA256 с отдельной случайной солью
и 600 000 итераций. Открытый пароль в объекте банка не сохраняется.
authenticate_client сравнивает хеши, возвращает bool, обнуляет счётчик
после успеха и блокирует клиента после трёх последовательных ошибок.
Неудачный вход также снимает отметку о ранее выполненном входе.

Перед открытием, поиском и сменой статуса Bank проверяет регистрацию,
статус клиента и выполненный вход. Для существующего счёта проверяет
принадлежность клиенту. open_account выбирает нужный класс, задаёт владельца
по Client и проверяет уникальность номера внутри банка.
freeze_account разрешён для активного счёта, unfreeze_account — для замороженного.
close_account разрешён для активного счёта без денег и вложений.
Закрытые счета сохраняются вместе с привязкой к клиенту.
search_accounts возвращает словари информации с необязательными фильтрами
по точному номеру и статусу.

Сеанс — отметка в памяти Bank, а не полноценная многопользовательская сессия.
Счета, открытые через Bank, получают внутреннюю проверку _bank_guard.
check_status() вызывает её перед денежными операциями, поэтому прямые вызовы
методов таких счетов также проверяют вход, принадлежность, блокировку и время.
Отдельные объекты счетов из упражнений дней 1–2 не получают ограничений Bank.
Общебанковские отчёты get_total_balance() и get_clients_ranking() описаны ниже.

## Общий баланс и рейтинг

get_total_balance() проходит по всем счетам и суммирует свободные остатки
в словаре валюта → Decimal. Между валютами конвертации нет.
Отрицательные балансы учитываются со знаком минус. Заморозка счёта
или блокировка клиента не исключает его из отчёта.
Вложенные в портфель средства не входят в свободные остатки.
Для пустого банка результат — пустой словарь.

get_clients_ranking(currency="RUB") проверяет валюту, затем для каждого
клиента суммирует его счета этой валюты. Возвращает список словарей
client_id, full_name, balance, currency, отсортированный по убыванию balance.
Клиенты без счетов входят с нулём; при равенстве сумм порядок регистрации
сохраняется. Для пустого банка результат — пустой список.
Вычисления используют общую точность Decimal: 50 значащих цифр.
Отчёты не меняют данные, доступны ночью и предназначены для управляющего
кода одного процесса. Авторизации роли администратора пока нет.

## Журнал и ночной запрет

Bank хранит события безопасности в памяти. Неверный вход, неизвестный или
заблокированный клиент, отсутствие входа, чужой счёт и ночная операция
записываются со временем, ID клиента, действием, причиной и номером счёта.
Пароли и хеши не журналируются. suspicious_actions возвращает копии записей.
Третья ошибка входа создаёт отдельную запись client_blocked.

Часы банка используют Asia/Colombo (UTC+05:30). Интервал запрета: 00:00 <= время < 05:00.
Проверка выполняется до изменения данных. Ночью запрещены изменение счетов,
пополнение, снятие, вложения и начисление процентов. Регистрация, вход,
поиск, чтение информации и расчёт прогноза разрешены.
В Bank(now=функция) можно передать часы для воспроизводимых проверок;
настоящие часы используются, если аргумент now не указан.

## Организация классов

AbstractAccount хранит общие данные и объявляет три абстрактных метода:
deposit(), withdraw(), get_account_info(). BankAccount реализует их.
SavingsAccount, PremiumAccount и InvestmentAccount наследуются от BankAccount
и переопределяют withdraw(), get_account_info(), __str__().
check_status() — общая проверка допустимости денежных операций.

## Создание счёта

1. BankAccount проверяет владельца, неотрицательный начальный баланс,
   статус, валюту и положительный лимит одного снятия.
2. Закрытый счёт допускается только с нулевым балансом.
3. Генерируется полный UUID для account_id. Если номер не передан,
   берётся остаток от деления числового UUID на 10^12 и строка дополняется
   нулями слева до 12 цифр. Переданный номер проверяется как строка из 12 цифр.
4. super().__init__() сохраняет общие данные в AbstractAccount.
5. SavingsAccount проверяет ставку, минимальный остаток и balance >= min_balance.
6. PremiumAccount проверяет неотрицательные овердрафт и комиссию.
7. InvestmentAccount создаёт портфель с нулевыми суммами stocks, bonds, etf.

Это логический порядок правил, а не требование к расположению строк в конструкторе.
При ошибке создание объекта прерывается.

## Проверки и Decimal

- to_decimal() преобразует int, float, строку или Decimal в конечный Decimal.
  Для дробных входных данных предпочтительны строки или Decimal.
- check_balance() допускает отрицательные денежные значения, но проверяет
  точность до копейки и модуль меньше 10^18.
- check_amount() дополнительно запрещает отрицательные суммы.
- check_rate() требует строго положительную месячную ставку.
- check_growth_rate() разрешает отрицательную, нулевую и положительную ставку.
  Ограничения: модуль меньше 10^18, до 28 значащих цифр,
  показатель десятичной степени не ниже -28.
- check_growth_rates() проверяет словарь активов и ставок.
- check_text() проверяет непустую строку и убирает пробелы по краям.
- check_asset() разрешает только stocks, bonds, etf.
- round_money() округляет вычисленный доход до копейки по ROUND_HALF_UP.

Сложение и вычитание денег не требуют округления в пределах модели.
При импорте utils.py задаётся getcontext().prec = 50 — общая точность
текущего контекста Decimal. Отдельные блоки localcontext() не используются.
Приложение однопоточное; для других потоков настройку нужно задавать отдельно.
Входная сумма 0.001 отклоняется, а вычисленный доход 0.005 округляется до 0.01.

## Пополнение — для всех типов

1. Проверить статус: frozen вызывает AccountFrozenError,
   closed — AccountClosedError, неизвестный — InvalidOperationError.
2. Проверить сумму через check_amount() и запретить ноль.
3. Рассчитать новый баланс = текущий баланс + сумма.
4. Проверить его через check_balance(), сохранить и вернуть.

Отрицательный итоговый баланс допустим для погашения овердрафта:
-1000 + 200 = -800. Комиссия за пополнение не берётся.

## Снятие с BankAccount

1. Проверить статус и положительную сумму.
2. Убедиться, что сумма не превышает текущий баланс.
3. Проверить лимит одного снятия; по умолчанию 100 000.
4. Вычесть сумму, сохранить и вернуть баланс.

Нехватка денег вызывает InsufficientFundsError,
превышение лимита — InvalidOperationError.

## Снятие с SavingsAccount

1. Проверить статус и сумму.
2. Если сумма больше баланса, вызвать InsufficientFundsError.
3. Рассчитать остаток = баланс - сумма.
4. Если остаток меньше min_balance, вызвать InvalidOperationError.
   Равенство минимуму допускается.
5. Вызвать super().withdraw(amount): родитель выполнит свои проверки и списание.

## Месячные проценты

1. Проверить статус.
2. Рассчитать доход = баланс × monthly_rate с общей точностью Decimal.
3. Округлить доход до копейки.
4. При нулевом доходе вернуть текущий баланс без deposit(0).
5. Иначе вызвать deposit(доход) и вернуть новый баланс.

Пример: 10 000 × 0.01 = 100; после начисления баланс 10 100.
Один вызов — одно начисление; календарь не отслеживается.

## Снятие с PremiumAccount

1. Проверить статус и положительную сумму.
2. Проверить лимит одного снятия; по умолчанию 500 000.
3. Рассчитать новый баланс = баланс - сумма.
4. Если он отрицательный, вычесть фиксированную overdraft_commission.
5. Если результат меньше -overdraft_limit, вызвать InsufficientFundsError.
6. Проверить денежный результат, сохранить и вернуть баланс.

Комиссия применяется при каждом снятии с использованием овердрафта.
При снятии до нуля комиссия не применяется. Граница -overdraft_limit допустима.
При отказе баланс не меняется.
Пример: 1000 - 1500 - 500 = -1000 при допустимом пределе -5000.

## Инвестиции

1. invest(asset, amount) проверяет статус, допустимость актива и положительную сумму.
2. При нехватке свободного баланса вызывает InsufficientFundsError.
3. Вычисляет и проверяет новую сумму в активе.
4. Уменьшает свободный баланс и увеличивает сумму актива на одинаковую величину.
5. Возвращает сумму, накопленную в этом активе.

InvestmentAccount.withdraw() использует родительское снятие:
вложенные деньги остаются в портфеле. Продажи активов нет.

## Прогноз годового прироста

1. Проверить словарь growth_rates: тип актива → годовая ставка в долях.
2. Для каждого актива с положительной суммой потребовать ставку.
3. Сложить произведения сумма актива × ставка с общей точностью Decimal.
4. Округлить общий прирост до копейки и вернуть его.

5000 × 0.10 + 3000 × 0.04 + 1000 × 0.07 = 690.
Нулевая и отрицательная прогнозная доходность допустимы.
Прогноз не меняет баланс или портфель и доступен независимо от статуса,
поскольку не является денежной операцией.

## Получение информации

get_account_info() возвращает новый словарь общих данных.
Наследники добавляют свои условия; InvestmentAccount возвращает копию портфеля.
Денежные значения и ставки остаются Decimal.
__str__() формирует строку с типом, владельцем, последними четырьмя цифрами
номера, статусом, балансом и валютой. SavingsAccount добавляет ставку и минимум,
InvestmentAccount — портфель.

## Ограничения

Данные не сохраняются между запусками. Номера из UUID не проверяются на
уникальность в постоянном хранилище. Банк поддерживает вход и смену статуса;
полноценные многопользовательские сеансы и конкурентные операции не реализованы.
Атрибуты открыты для изменения по правилам Python; проверки гарантируются
при использовании предусмотренных методов, а не при ручном изменении полей.

## Очередь транзакций

Transaction создаётся в статусе created. Проверяются клиент, номера, положительная
сумма, валюта и тип: internal_transfer или external_transfer.
При добавлении проверяются целый priority, отсутствие дубликата и execute_at
с часовым поясом. Статус становится pending, объект добавляется в список.

get_next() просматривает список и рассматривает только pending и retry_pending.
Будущие execute_at и next_attempt_at пропускаются. Выбирается наибольший priority;
при равенстве — первый добавленный. Выбранный объект становится processing.
cancel() допускается только для pending/retry_pending. История остаётся в списке.

## Обработка перевода

1. Processor увеличивает attempts и определяет внутренний или внешний перевод.
2. Внешний перевод требует другого объекта Bank; недоступность внешнего банка
   до списания вызывает TemporaryTransactionError.
3. Bank.transfer проверяет вход и принадлежность отправителя, статусы счетов,
   ночной запрет в обоих банках, сумму, валюту и лимит одного снятия.
4. Рассчитывается остаток отправителя после суммы и внешней комиссии.
   Обычным счетам отрицательный результат запрещён; SavingsAccount сохраняет минимум.
   PremiumAccount допускает долг в пределах овердрафта с учётом его комиссии.
5. Сумма перевода умножается на заданный курс пары валют получателя.
   Результат округляется до копейки, нулевое зачисление запрещается.
6. Проверяются оба новых баланса. Только после всех проверок они сохраняются.
   В однопоточном приложении между этими присваиваниями нет операций,
   способных вызвать обычный отказ валидации.
7. Transaction получает completed, размер комиссии, сумму и валюту зачисления,
   использованный курс и время завершения. Повторный запуск не списывает деньги заново.

Валюта транзакции — валюта отправителя. Внешняя комиссия фиксированная,
по умолчанию 10 единиц, комиссия овердрафта добавляется при отрицательном итоге.
Внутренний перевод не имеет внешней комиссии. Получатель не обязан быть
авторизован для зачисления, но его блокировка и статус счёта проверяются.
Перевод самому себе на тот же счёт запрещён. Курсы не загружаются из сети.

## Отказы и повторы

Все ошибки обработки записываются в processor.errors с ID, попыткой, временем,
типом и причиной. Обычные ошибки завершают операцию статусом failed.
Только TemporaryTransactionError переводит её в retry_pending с будущим
next_attempt_at, если попытки ещё остались. По умолчанию максимум 3 попытки,
между ними минимум 60 секунд. После исчерпания попыток — failed.
Отменённые операции и ожидающие повторы не меняют балансы.
Автоматического фонового планировщика нет: process_ready() вызывается повторно.

В демонстрации используется 10 операций: 5 completed, 4 failed, 1 cancelled.
Внешний перевод сначала недоступен и завершается со второй попытки.
Отсроченная операция выполняется после перевода демонстрационных часов на 2 минуты.
Время задаётся явно в UTC, реальные ожидания не используются.
Очередь, транзакции и защита от повторного выполнения существуют только в памяти;
восстановление после аварий и распределённые банковские переводы не реализованы.

## Аудит и риск

Bank создаёт AuditLog с отдельным JSONL-файлом и RiskAnalyzer.
Зависимости можно передать в конструктор для своей настройки или проверки.
События регистрации, успешного входа, смены статуса счетов и безопасности
поступают в аудит. Оценки риска и результаты переводов записываются с ID транзакции.
Процессор дополняет аудит отказами и временными ошибками повторных попыток.

AuditLog.record() создаёт копию данных, добавляет время, важность и контекст,
сохраняет запись в памяти и дописывает строку JSON в файл.
Decimal и datetime в деталях сериализуются строками. При ошибке диска
запись остаётся в памяти с persisted=False, ошибка добавляется в file_errors.
Старые записи читаются при открытии существующего файла. filter() возвращает
глубокие копии записей с фильтрами по уровню, клиенту, транзакции, событию,
риску и временному интервалу. Секреты авторизации не передаются в аудит.

Bank.transfer() анализирует перевод до статусов и финансового списания,
но после первичной проверки владельца, суммы, валюты, лимита и номеров.
Анализатор начисляет баллы за крупную сумму, частоту, нового получателя и ночь:
крупный порог или 10 операций за 60 секунд дают 3 балла,
половина крупного порога или 5 операций — 1 балл, новый получатель — 1,
ночь по времени банка — 3. Баллы сигналов суммируются.
0 означает low, 1–2 medium, 3 и больше high.
Пороги сумм заданы по валютам и настраиваются.

В историю попадают уникальные ID анализированных операций клиента.
Окно частоты: now - 60 секунд < время <= now, включая текущую операцию.
Неудачный перевод учитывается, если он дошёл до анализа; повтор того же
ID обновляет запись, не увеличивая число операций.
Новый получатель определяется парой bank_id и account_number.
Он становится знакомым только после успешного изменения балансов.

При high банк записывает critical/risk_assessed и вызывает RiskBlockedError.
Процессор ставит failed без повторов. При medium записывается warning,
при low — info; остальные правила счёта продолжают действовать.
После успешного перевода история отмечает completed и запоминает получателя.
Риск не блокирует клиента целиком, только конкретную операцию.
Прямые денежные методы счетов не используют поведенческий RiskAnalyzer;
его граница интеграции в этой версии — переводы Bank.transfer().

suspicious_operations() выбирает оценки medium/high и события безопасности.
client_profile() возвращает максимальный исторический риск, число операций,
успехов, блокировок, причин и знакомых получателей.
error_statistics() группирует записи с error_type по классу ошибки;
каждая попытка учитывается отдельно, оценка риска сама по себе не удваивает ошибку.
История анализатора существует в памяти, файл сохраняет аудит, а не всё состояние банка.

## Комплексный сценарий дня 6

1. create_demo() создаёт общие демонстрационные часы, один банк, очередь,
   процессор, 6 клиентов и 12 счетов. Все клиенты регистрируются и входят.
   Один накопительный счёт замораживается; в инвестиционный портфель
   переводится 3000 RUB. Начальные свободные остатки — 184000 RUB и 500 USD.
2. fill_queue() создаёт 40 Transaction и записывает их добавление в аудит.
   Первые 18 — обычные переводы. Остальные показывают приоритет, нехватку
   денег, заморозку сторон, неизвестный номер, нового получателя, крупные суммы,
   неправильную валюту, перевод самому себе, минимальный остаток,
   овердрафт, лимит, конвертацию, отмену, ночной запрет и частоту.
3. process_queue() сортирует моменты готовности и переводит на них часы.
   Процессор выбирает готовые операции по приоритету. Реальные задержки
   и фоновые потоки не используются. После каждого результата выводится
   статус и причина отказа либо сумма зачисления и комиссия.
4. print_reports() показывает счета выбранного клиента, историю его входящих
   и исходящих операций, подозрительные записи, топ-3 клиентов в RUB,
   статистику всех статусов, ошибки, свободные остатки и отдельный портфель.

Все 40 операций достигают конечного статуса: 27 успешны, 12 отклонены,
1 отменена без обработки. Топ-3 и балансы воспроизводимы, UUID случайны.
Банковская комиссия овердрафта уменьшает свободные остатки на 500 RUB;
конвертация уменьшает RUB на 100 и увеличивает USD на 1.
Итог: 183400 RUB и 501 USD свободных средств, 3000 RUB в портфеле.

## Отчётность и визуализация дня 7

1. ReportBuilder получает банк и список транзакций. Сбор отчётов не меняет
   счета, статусы транзакций или журнал аудита.
2. Для отчёта клиента выбираются его счета и связанные входящие/исходящие
   транзакции. Остатки складываются отдельно для каждой валюты.
3. Для банка подсчитываются все статусы транзакций, собираются свободные
   остатки по валютам, топ-3 в выбранной валюте и статистика ошибок.
4. Для рисков подсчитываются только события risk_assessed, чтобы результат
   обработки одной операции не дублировал её оценку. Подозрительные события,
   профили клиентов и ошибки берутся из существующих методов аудита и риска.
5. build_text() обходит вложенные данные и формирует текст с отступами.
   export_to_json() сохраняет структуру, export_to_csv() разворачивает её
   в пары field/value с путями вида accounts[0].balance. Decimal сериализуется
   точной строкой, Enum — значением, время — строкой ISO.
6. save_charts() сохраняет круговую диаграмму статусов, горизонтальные столбцы
   свободных балансов по клиентам и ступенчатую историю выбранного счёта.
   Валюты не складываются между собой, инвестиционный портфель не прибавляется
   к свободным деньгам. float используется только при рисовании matplotlib.

При открытии счёта аудит запоминает начальный баланс и валюту. Затем банк
подключает к счёту функцию записи balance_changed: успешные денежные методы
вызывают её после изменения баланса. Перевод записывает снимки обеих сторон
после сохранения обоих новых балансов. Неудачная операция снимка не создаёт.
get_balance_history() выбирает снимки по номеру счёта и упорядочивает по времени.
Старые события без баланса пропускаются; при отсутствии данных график показывает
сообщение вместо выдуманной истории.

run_reports() выполняет демку дня 6, строит три отчёта, сохраняет каждый
в TXT, JSON и CSV, затем создаёт три PNG. Каталог по умолчанию reports/day7/.
Графики сохраняются без GUI через backend Agg; после сохранения фигуры закрываются.
